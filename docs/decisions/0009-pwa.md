# ADR 0009 — Progressive Web App (installable, offline-capable)

**Status:** Accepted — 2026-06-01

## Context

BSC Lab is a client-only static app served from GitHub Pages (CLAUDE.md §2).
That makes it an unusually good fit for Progressive Web App (PWA) packaging:
the same static `dist/` that Pages serves can be precached by a service worker,
giving an installable, offline-capable app at near-zero infrastructure cost.

The motivating value is concrete:

1. **Installable** — a home-screen/desktop launcher for the stimulation player
   and the knowledge browser, in a standalone window without browser chrome.
2. **Offline sessions** — once visited, a user can run a stimulation session
   (audio worklets, WASM oscillator, ambient samples) with no network.
3. **Offline knowledge browsing** — the ontology Turtle files and the SPARQL /
   graph engines work without a connection after first use.

The question this ADR answers is *not* "can we" — SvelteKit + `adapter-static`
makes the base case trivial — but **"what does a service worker break, and how
do we constrain it so it breaks nothing."** Three hazards are specific to BSC
Lab's architecture and are treated here as binding constraints, not advice. They
are specified in full in
[`../technical/PWA_SERVICE_WORKER.md`](../technical/PWA_SERVICE_WORKER.md); this
ADR records *why* each constraint exists.

### Trap 1 — an update must never reload during a session

A precaching service worker serves the *previously cached* app shell after a new
version deploys, until the new worker activates. The common recipe pairs
`skipWaiting()` with an automatic `location.reload()` the moment a new worker is
ready. For most sites that is a minor flicker. For BSC Lab it would **terminate
an in-progress stimulation session** — audio playback, breathing guidance, and
any visual/haptic entrainment — mid-stream. That is a worse failure than running
a slightly stale build.

### Trap 2 — the service worker must not intercept Firebase or any cross-origin request

BSC Lab uses optional Firebase auth + Firestore
([`../../src/firebase/`](../../src/firebase/)) and Google sign-in via popup.
These are dynamic, cross-origin, credentialed requests to `*.googleapis.com`,
`identitytoolkit`, Firestore, and `accounts.google.com`. A naïve cache-first
`fetch` handler that touches them serves stale auth state or blank live data and
can break sign-in outright.

### Trap 3 — the ambient samples must not be eagerly precached

SvelteKit's `$service-worker` `files` array contains *everything* in `static/`.
Precaching all of it on install would pull the three ambient sample clips
(`static/audio/*.wav`, ~948 KB each, **2.8 MB total**) and all ontology Turtle
(~140 KB) into the cache before the user has touched either feature — a slow,
wasteful install. The worklet + WASM kernel, by contrast, total **~40 KB** and
are required for any session, so they *should* be precached.

### A tempting fourth option, deliberately declined

A service worker is the known workaround for the COOP/COEP limitation in
CLAUDE.md §9: GitHub Pages cannot send `Cross-Origin-Opener-Policy` /
`Cross-Origin-Embedder-Policy`, which blocks `SharedArrayBuffer` and threaded
WASM audio. The `coi-serviceworker` pattern *injects* those headers from the
worker, enabling cross-origin isolation on Pages. It is genuinely tempting — it
would unlock threaded WASM audio without leaving Pages. It is **not** adopted
here because `COEP: require-corp` then requires every cross-origin resource to
carry CORP/CORS headers, which re-breaks Firebase (Trap 2) and any future CDN
dependency. See Consequences and Alternatives.

## Decision

**Ship BSC Lab as an installable, offline-capable PWA, using SvelteKit's native
service worker — not `vite-plugin-pwa`.** The implementation is bound by the
three constraints above.

1. **Manifest + icons.** Add `static/manifest.webmanifest` (`display:
   standalone`, `start_url`/`scope` `/`, `theme_color` matching the default
   *paper* skin) and PNG icons (192, 512, 512-maskable, 180 apple-touch),
   generated from the existing brand mark in
   [`../../static/favicon.svg`](../../static/favicon.svg).

2. **Native service worker** at
   [`../../src/service-worker.js`](../../src/service-worker.js), compiled by
   SvelteKit/Vite via the `$service-worker` module (`build`, `files`,
   `prerendered`, `version`). No new dependency. `vite-plugin-pwa` is rejected
   because it duplicates and fights SvelteKit's own service-worker pipeline.

3. **Caching strategy** (Trap 3):
   - **Precache** the hashed app build, the prerendered route shells, and the
     worklet + WASM kernel (`/worklets/*`) — everything needed to launch and run
     a session offline, ~small.
   - **Runtime-cache** (network-first, fill on first use) the ambient samples,
     the ontology Turtle, and icons — the heavy/optional assets.

4. **Cross-origin bypass** (Trap 2): the `fetch` handler responds *only* to
   same-origin `GET`. Cross-origin requests (Firebase, Google sign-in, any CDN)
   and range requests are not intercepted — they go straight to the network.

5. **Session-safe update flow** (Trap 1): the worker **never** calls
   `skipWaiting()` on its own. A new version installs and *waits*. A passive,
   dismissible banner
   ([`../../src/ui/pwa/ServiceWorkerUpdate.svelte`](../../src/ui/pwa/ServiceWorkerUpdate.svelte))
   tells the user an update is ready; the reload happens **only** on explicit
   user action, which posts `SKIP_WAITING` to the waiting worker. There is no
   automatic reload anywhere.

6. **Registration only in production.** SvelteKit auto-registration is disabled
   (`kit.serviceWorker.register = false`); the app registers the worker manually
   in the update component, guarded by `!dev`. This keeps the service worker out
   of the `make dev` loop, where a precaching worker would serve stale assets and
   fight HMR (a known time-sink — see the browser-verification workflow notes).

## Consequences

- BSC Lab becomes installable and runs sessions and the knowledge browser
  offline, with **no change to hosting** — still GitHub Pages, still static.
- The three-clock audio architecture and the worklet invariants (CLAUDE.md
  §3.1–3.3) are **untouched**. A service worker runs on its own thread, never
  sees `AudioContext`, and intercepts network I/O only. There is no interaction
  with audio timing.
- Deployments never interrupt an active session. Users adopt a new version when
  they choose to; the trade-off is that a user who ignores the banner keeps
  running the previous build until they reload — acceptable and intended.
- Firebase auth/Firestore and Google sign-in are unaffected, because the worker
  never intercepts them.
- The ambient samples and ontology are fetched and cached lazily, so first
  install stays light; their first *use* still requires a network round trip
  (then they are available offline).
- Precaching includes the lazily-loaded Comunica (~500 KB) and Cytoscape chunks,
  so SPARQL and the graph view work offline. This is a deliberate trade: the
  bytes are cached in the background after first load, not added to the initial
  page download, so CLAUDE.md §9's lazy-load goal (keep them off the *startup*
  path) is preserved.
- `SharedArrayBuffer` / threaded WASM audio remains **blocked on GitHub Pages**.
  This ADR does not unblock it; the COEP-injection route was declined (see
  below). The migration path in CLAUDE.md §9 (move runtime hosting to a
  custom-header host) is unchanged.
- New session-relevant moving part: the update banner. It is intentionally
  passive and carries no medical/health copy (CLAUDE.md §3.5).

## Alternatives considered

**`vite-plugin-pwa` (Workbox).** Mature, batteries-included precaching and
update prompts. Rejected: it overlaps SvelteKit's own `$service-worker`
pipeline, adds a dependency and a second source of truth for the asset list, and
its default auto-update behaviour is exactly the session-killing reload of Trap
1. SvelteKit's native worker is lower-dependency and gives direct control over
the install set and the update flow.

**Auto-update (`skipWaiting` + immediate reload).** The common default and the
`vite-plugin-pwa` `registerType: 'autoUpdate'` behaviour. Rejected outright: it
interrupts active sessions (Trap 1).

**Precache everything in `files`.** The simplest install handler. Rejected:
pulls 2.8 MB of ambient samples and all Turtle into the cache before first use
(Trap 3).

**COEP-injecting service worker (`coi-serviceworker`) to unlock
`SharedArrayBuffer` on Pages.** Tempting, because it would enable threaded WASM
audio without leaving GitHub Pages. Rejected *for now*: `COEP: require-corp`
makes every cross-origin resource fail unless it sends CORP/CORS, which breaks
Firebase (Trap 2) and any CDN. If threaded WASM audio is ever pursued on a host
that still can't set headers, revisit this with `COEP: credentialless` and an
explicit Firebase compatibility test — as its own ADR, not a quiet addition.

**Cache-first navigations.** Faster repeat loads, but serves a stale shell after
deploy and couples poorly with the session-safe update model. Rejected in favour
of network-first navigations with a cache fallback (fresh when online, offline
when not).
